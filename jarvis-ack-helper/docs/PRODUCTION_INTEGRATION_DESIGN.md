## Mandatory requirements for integration

**R1 — Request correlation.** `PLAY <id>` / `STARTED <id>` /
`ENDED <id> ok=<bool>`, where `id` is a bounded unsigned integer (UInt64)
generated by the runtime. It is compared for equality and used for nothing
else. It must never reach a path, an asset name, a shell, a URL, a filesystem
call or a volume control. This is the only parameter any message carries.

**R2 — Matching rule.** While waiting on request N, only `STARTED N` and
`ENDED N` count as that turn's response. Any other id is `STALE_RESPONSE` and is
discarded. **Receiving one line is not completion** — the wait ends on a
matching `ENDED` or on the timeout, and on nothing else. Draining the socket
before each PLAY is not an acceptable substitute: it only works if the stale
line has already arrived, which is a race.

**R3 — Timeout.** `ACK_TIMEOUT = 1.5 s`, from the worst observed 717.03 ms with
783 ms of headroom (2.09x). On expiry: `ACK_FAILED(reason=timeout)` → COMMAND.
Command acceptance never stops.

**R4 — Late responses.** An `ENDED <old_id>` arriving after a timeout must never
be applied to a later turn. This was measured, not hypothesised: turn B
"completed" in 0.2 ms on turn A's stale reply, which in production would open
command capture while the acknowledgement was still audible — the exact
self-echo the ACKNOWLEDGING gate exists to prevent. R1 makes the prevention
structural.

**R5 — Health policy.** One ACK timeout marks the helper UNHEALTHY. While
unhealthy the ACK is skipped outright and wake → COMMAND returns to today's
~251 ms. Recovery is a `PING` → `PONG`, and that probe must stay **off the wake
critical path** — a health check must not add latency to a turn, and must not
make a sound the user did not earn. Recorded as a design requirement; not
implemented, and no threshold is fixed.

## Production gate

ACK integration does not begin until Shared Stream validation completes:

```
noise gate -> 1-turn -> 3-turn -> 10-turn -> 20-turn -> long-idle turn
```

Then: ACK integration → 3–10 turns with the ACK → HUD live E2E → Phase 1C
finalization.

## What the launchd validation established

The prototype was previously only proven from a terminal, which is not where
the runtime lives. Under a temporary LaunchAgent (`local.jarvis.ack-helper-test`,
since removed):

```
PLAYBACK_WORKED   40/40   (10 TCC-gate plays + 30 timed + 1 after idle)
TCC_PROMPT        none
TCC log entries   none for this binary
crashes           0
stderr            empty
```

Timing, 30 plays under launchd against the terminal baseline:

| | p10 | p50 | p90 | min | max |
|---|---|---|---|---|---|
| trigger → play() call | 0.05 | 0.08 | 0.14 | 0.05 | 0.15 |
| trigger → play() returns | 10.42 | 13.13 | 21.60 | 7.41 | 48.50 |
| **trigger → end (launchd)** | 669.58 | **674.69** | 681.39 | 667.84 | 709.11 |
| trigger → end (terminal) | 674.05 | **677.34** | 680.27 | 666.54 | 712.44 |

The launchd context is not slower — 674.69 vs 677.34 ms, a difference well
inside the spread. Idle for 609 s: **CPU 0.0000 s, RSS unchanged at 25.6 MB**,
and a PING answered afterwards, followed by a successful play.

The validation needed no change to the helper. launchd cannot type, so stdin
was pointed at a FIFO via `StandardInPath` and a driver wrote `PLAY` into it —
the same three-command interface, exercised through a different pipe.

One observation: the first play after ten minutes idle took 54 ms to return
against a typical 13 ms, and 713 ms end to end against 675 ms. Small, but it
suggests something warms up. Not investigated; recorded so it is not mistaken
for noise later.

## Proposed production IPC — Unix domain socket

stdin was right for measuring and wrong for production: it ties the helper's
lifetime to whoever owns the pipe, so a runtime restart would take the helper
with it. A socket separates the two lifecycles — the helper survives a runtime
restart, and the runtime does not own or supervise the helper process.

IPC cost is not a consideration either way: the prototype's pipe added ~0.3 ms
against the helper's own internal timestamps, so a socket will not move the
928 ms budget.

```
SOCKET_LOCATION     ~/Library/Application Support/Jarvis/ack-helper.sock
SOCKET_PERMISSIONS  0600 socket, inside a 0700 directory
```

Not `/tmp`: a fixed path in a world-writable directory can be pre-created by
another user, and on a shared machine that is a hijack. The containing
directory must be user-owned and mode 0700 so the path cannot be substituted.
The helper must unlink a stale socket only after confirming it owns the
directory, and must refuse to run if the directory has unexpected ownership.

## IPC protocol — correlation IDs are REQUIRED, not optional

A bare `PLAY / STARTED / ENDED` protocol has a demonstrated cross-talk bug once
a timeout exists. Measured, not theorised:

```
turn A  PLAY -> STARTED, timeout at 1502.0 ms, JARVIS proceeds to COMMAND
        (helper's ENDED arrives ~200 ms later, into a socket nobody is reading)
turn B  PLAY -> "completes" in 0.2 ms
        line consumed: "ENDED seq=1 ok=true late=true"   <- turn A's
```

Turn B believed its acknowledgement had finished before a single sample played.
In production that means the ACK is still audible when command capture opens —
which is exactly the self-echo the whole ACKNOWLEDGING gate exists to prevent.

Draining the socket before each PLAY papers over it, and that is what the
validation harness did, but it is a race: it works only if the stale line has
already arrived. An ID makes the guarantee structural.

```
->  PING                    liveness
->  PLAY <id>               play the ACK, id = small unsigned integer
->  STATUS                  IDLE | PLAYING            (optional)

<-  PONG
<-  STARTED <id>
<-  ENDED   <id> ok=<bool>
<-  PLAY_IGNORED <id> reason=already_playing
<-  ERROR   <id> <reason>
```

The client ignores any reply whose id is not the one it is waiting for. This is
the ONE exception to "no message carries a parameter", and it is deliberately
the narrowest possible one: a bounded integer, generated by the client,
compared for equality and never used for anything else. It cannot name a file,
select an asset or reach a filesystem. The asset stays a compile-time constant.

Maximum message length stays fixed and small (32 bytes covers the longest verb
plus an id); anything longer is discarded without parsing. Still no file path,
no URL, no arbitrary text, no shell, no volume control, no asset selection, no
JSON payload.

## Play policy

```
IDLE    + PLAY  ->  play, emit STARTED then ENDED
PLAYING + PLAY  ->  PLAY_IGNORED
```

No queue. Two wake words in quick succession must not produce 「はい」「はい」.
Already verified in the prototype.

## Completion signalling — not a fixed sleep

The runtime must wait for `ENDED`, never for a hard-coded 575 ms. The clip is
575 ms but end-to-end was 667–713 ms, and the gap is output buffering the API
does not expose. A fixed sleep would either cut the ACK off or pad every turn.

```
PLAY -> STARTED -> ENDED -> COMMAND
```

## ACK timeout — the failure this creates

Waiting for `ENDED` introduces a way to hang: if the helper dies mid-play, no
`ENDED` ever arrives and the turn stops before command capture. So the wait
needs a ceiling, after which the runtime proceeds regardless.

The value is not decided here. It should come from measurement, as the
watchdog's 45 s did: the observed maximum is 713 ms, so a ceiling somewhere
above that with real margin, not a round number chosen for looking tidy.

```
PLAY sent
  -> ENDED within the ceiling   -> COMMAND
  -> ceiling reached            -> ACK_TIMEOUT -> COMMAND anyway
```

This is a **UX fallback, not a security decision**, and it is entirely separate
from the CoreAudio input watchdog. The two must not be conflated: the watchdog
restarts a process to recover a deadlocked microphone; this one skips a
courtesy sound.

## Helper failure policy — fail-open on the sound only

```
helper unavailable / connect fails / play fails / timeout
  -> skip the ACK
  -> proceed to COMMAND
```

JARVIS must never stop accepting commands because a 「はい」 could not play.
Again: this is fail-open for an audio cue. It has no bearing on the
deterministic security gate or on approvals, and must not be cited as
precedent for those.

## State machine

```
WAKE -> ACKNOWLEDGING -> COMMAND -> WAKE
```

During ACKNOWLEDGING:

```
physical input stream   ACTIVE      (never opened, started, stopped or closed)
wake consumer           PAUSED
command consumer        DISCARD
ACK helper              PLAYING
```

On `ENDED` (or `ACK_TIMEOUT`), ownership moves to COMMAND.

The invariant that this whole audio phase exists to protect must hold:

```
PA_OPEN_COUNT  = 1
PA_START_COUNT = 1
```

Adding the ACK must not cause a single `InputStream` open, start, stop or
close. This fits the existing design rather than fighting it — `_recording`
already gates the wake consumer, and ACKNOWLEDGING is one more window in which
neither consumer takes frames. The ACK is output; it never touches input.

## Latency budget — the serial estimate was wrong

The 926 ms figure assumed `pause_listening` and the ACK run one after the
other. They do not have to. The shared stream never stops the physical input
stream, so releasing the wake detector and playing a sound are independent, and
running them concurrently collapses the cost to the longer of the two.

Measured over 100 handoffs against the real shared stream, the real detector in
`external_audio` mode, and the real helper over a Unix socket:

| | p10 | p50 | p90 | max |
|---|---|---|---|---|
| wake → ACKNOWLEDGING | 0.00 | **0.00** | 0.01 | 0.02 |
| wake → STARTED | 10.42 | **15.00** | 20.43 | 61.42 |
| pause_listening duration | 184.28 | **214.78** | 247.01 | 255.69 |
| ACK duration | 671.49 | **676.23** | 681.24 | 717.03 |
| **wake → COMMAND ready** | 671.86 | **676.68** | 681.75 | 722.66 |

```
serial estimate    926 ms
parallel measured  677 ms      -249 ms, and it is now bounded by the ACK alone
```

`WAKE_TO_COMMAND_READY` (676.68) equals `ACK_DURATION` (676.23) to within half a
millisecond, which is the check that matters: `pause_listening` has completely
disappeared into the ACK's shadow. Nothing is serialised.

The mode flip itself costs 0.00 ms, so gating the consumers before playing
anything is free.

`pause_listening` is now off the critical path entirely, which removes the
reason to optimise it. It would only matter again if the ACK got shorter than
~215 ms.

## Self-echo, structurally

Across all 100 handoffs and all 5 failure cases:

```
frames delivered to the wake consumer during ACKNOWLEDGING     0
frames delivered to the command consumer during ACKNOWLEDGING  0
frames received after switching to COMMAND                     >= 9
```

Zero is not a tuning result; it follows from the ordering. `detach()` runs
before PLAY is sent, and `_recording` is still false, so neither consumer is
reachable while the sound plays. The frames after COMMAND confirm the gate
opens again.

`PA_OPEN_COUNT = 1`, `PA_START_COUNT = 1`, `replacements = 0` throughout.

## Failure behaviour — measured, not asserted

Five ways for the ACK to fail. In every one, COMMAND was reached and 12 frames
were captured:

| case | ACK failed | COMMAND reached | wake → command |
|---|---|---|---|
| helper absent (never started) | yes | yes | 126 ms |
| healthy (control) | no | yes | 835 ms |
| connection closed before PLAY | yes | yes | 379 ms |
| helper killed after STARTED — no ENDED ever | yes | yes | 379 ms |
| helper dead, reconnect fails | yes | yes | 307 ms |

A broken ACK is *faster* than a working one, which is the right shape: the user
loses the courtesy sound and loses nothing else.

The fourth case is the one the timeout exists for — the helper is killed
mid-playback, so `ENDED` never arrives. It completed in 379 ms because the
socket closed and the read failed; a helper that hung without closing its socket
would need the ceiling.

## Recommended ACK timeout

Observed worst case across every run: **717 ms** (100-cycle max 717.03, launchd
30-cycle max 709.11, first play after 10 min idle 713.11).

| candidate | headroom over worst observed | cost when it fires falsely |
|---|---|---|
| 1.25 s | 533 ms (1.74x) | +574 ms |
| **1.5 s** | 783 ms (2.09x) | +824 ms |
| 2.0 s | 1283 ms (2.79x) | +1324 ms |

**1.5 s** is the recommendation: a bit over 2x the worst observation, which
matches the margin used for the watchdog's 45 s, while a false fire costs under
a second. 1.25 s is defensible but only 1.74x, and the tail here is not well
characterised — one sample already showed an outlier after idle. 2.0 s buys
margin nobody has evidence of needing and doubles the penalty when it fires.

Not set anywhere. This is a recommendation.

## Open-socket timeout — validated

The earlier failure cases all ended the connection, and the client noticed in
under 400 ms. The case that actually needs a ceiling is the one that announces
nothing: STARTED arrives, the socket stays open, the process stays alive, and
ENDED never comes. A fake helper was built to produce exactly that (it plays no
audio and touches no CoreAudio API — nothing in this test can wedge the input
path), and driven against the REAL shared stream and the REAL wake detector.

10 consecutive hangs, `ACK_TIMEOUT = 1.5 s`:

| | min | p50 | p90 | max |
|---|---|---|---|---|
| PLAY → STARTED | 0.07 | 0.13 | 0.19 | 0.19 |
| STARTED → timeout | 1500.32 | **1501.05** | 1502.02 | 1502.02 |
| wake → COMMAND | 1651.88 | **1655.15** | 1660.87 | 1660.87 |

```
STARTED received      10/10
ENDED received         0/10        (by construction)
fired on timeout      10/10
COMMAND reached       10/10        14-15 frames captured every time
helper still alive     yes
socket still open      yes         (PING answered PONG afterwards)
self-echo wake/command 0 / 0
PA_OPEN_COUNT 1  PA_START_COUNT 1  replacements 0
```

The timeout is accurate to within 2 ms of 1500 — scheduler jitter and nothing
else. There is no unbounded wait.

Recovery: after ten consecutive timeouts, three normal plays completed at
665.1 / 663.1 / 663.4 ms. One timeout does not break the ACK.

## ACK health policy — recommended, not implemented

Every timed-out turn costs the user 1.5 s of silence before they may speak. Ten
in a row cost 15 s for an acknowledgement that never plays. Consecutive
timeouts should mark the helper unhealthy and skip the ACK outright:

```
timeout          -> mark unhealthy
while unhealthy  -> skip the ACK entirely; wake -> COMMAND at today's ~251 ms
periodically     -> one cheap PING; a PONG restores healthy
```

PING rather than a speculative PLAY, because a probe that succeeds should not
make a noise the user did not earn. Whether one timeout is enough to trip it or
it should take two is a judgement about how often a spurious timeout is
expected — and the measured margin (2.09x over the worst observation) suggests
rarely, which argues for tripping on the first.

Not implemented. No threshold chosen.

## Not decided, and not to be assumed

- The exact ACK timeout value.
- Whether the final asset is P050, P060 or P070 — P060 is a benchmark baseline,
  not a human selection.
- Whether the helper gets its own LaunchAgent, and with what `KeepAlive`
  policy. None exists.
- Whether the HUD gains an `ACKNOWLEDGING` state. `JarvisPhase` already decodes
  unknown states tolerantly, so the runtime could publish it before the HUD
  understood it — but nothing has been added.
- Whether the ACK using the Chatterbox voice while replies use Edge TTS is
  acceptable.
